# Agent 写得更快之后，开源项目处理得过来吗？

2026 年，我们重新整理 Agentic AI 开源全景图时，最先看到的是一轮很直观的扩张。

新的 coding agent、个人助手和多 Agent 应用不断出现；memory、context、协议、工具调用、sandbox、observability 等项目也沿着 Agent 完成任务的路径生长。很多产品已经开始读取仓库、调用工具、修改代码，再把结果交回给人。

如果只看项目数量和 OpenRank，这个生态正处在很旺盛的阶段。但当我们把视线移到 GitHub 的 Issue、Pull Request 和 Review 记录上，另一组数字开始变得醒目：代码进入仓库的速度，已经明显快过一部分项目处理代码的速度。

在同一组 55 个高活跃仓库中，2026 年前八个月收到 26.5 万条 PR，去年同期是 13.0 万条，增长了 105%。同期关闭的 PR 有 22.3 万条，流入与关闭之间留下 4.28 万条差额。90 天后仍未处理完成的 PR 比例，也由 5.5% 上升到 11.3%。

Agent 的确让更多代码被写出来、被检查、被修改。它有没有让开源项目更高效，却不能只看生成速度。一个 patch 进入公共仓库以后，还要等待回应、接受 Review、继续修改、通过测试，并由有权限也愿意承担后果的人决定是否合入。我们这次想追踪的，正是这条公开协作链路。

本文使用三层数据。第一层是 84 个 Agent Infra 项目和 59 个 Model Infra 项目组成的 2026 全景图；第二层是 2026 年 7 月 OpenRank 最高的 100 个仓库及其完整 Issue / PR 记录；第三层从这 100 个仓库各抽取 50 条公开线程，共 5,000 条，用来还原谁发起、谁回应、谁 Review、谁继续提交，以及谁完成最后一个公开动作。涉及 2026 年的统计均截止到 8 月 31 日。

## 一张正在向 Runtime 延伸的 Agentic AI 全景图

当前全景图收录 143 个项目，其中 Agent Infra 84 个，Model Infra 59 个。Agent Infra 进一步分为 Application、Framework 和 Runtime；Model Infra 则包括 Serving、Pre-Train、Data、Compute 和 Post-Train。

Application 仍然聚集了最多活跃度。32 个 Application 项目占 Agent Infra 项目数的 38%，却贡献了 7 月 OpenRank 的 55%。这里有 coding agent、个人助手、工作流和其他直接面向用户的产品。它们离需求最近，迭代也最快。

Runtime 的信号不同。31 个 Runtime 项目只占 Agent Infra 7 月 OpenRank 的 22%，但在本轮新进入研究范围的 23 个 Agent Infra 项目中，Runtime 有 13 个。新增项目集中在 memory、context、协议互操作、工具调用、执行隔离和运行证据等位置。生态关注点正在沿着任务执行链向下移动。

> 【配图 1：在线报告「Agent Infra 与 Model Infra Landscape 2026」双全景图。建议截取两张全景图并排的完整区域。】

这一变化在 coding 领域尤其清楚。全景图里有 14 个 Agentic coding 项目和 8 个 coding workflow / harness 项目，是最大的应用集群。代码工作天然适合 Agent：仓库提供明确的工作区，测试可以执行，diff 可以比较，Review 记录公开，失败后还能继续修改。它给了 Agent 一条相对完整的反馈路径。

应用能够修改代码之后，新的工程问题随之出现。Agent 需要知道该读取哪些上下文，怎样调用工具，临时权限什么时候失效，代码应该在哪个隔离环境运行，任务中断后如何恢复，最后又留下什么证据。全景图中的 9 个 memory、knowledge 与 context 项目，8 个 protocol 与 interoperability 项目，6 个 tool、web 与 computer use 项目，以及 sandbox、observability 项目，对应的正是这些环节。

4 月至 7 月的 OpenRank 变化也呈现出相近方向。Lark CLI 增长 83.9，OpenViking 增长 42.6，FlashInfer 增长 20.7；DeepSeek Reasonix、Orca 和 Deer Flow 也进入增长前列。活跃度增量既出现在直接执行任务的工具，也出现在上下文管理、多 Agent 编排和推理效率上。

> 【配图 2：在线报告「4 月至 7 月 OpenRank 增长前六」。建议截取 APR→JUL 标题、左侧分析文字和右侧六个项目条形排名。】

项目年龄进一步说明了两层生态的差异。Agent Infra 中有 55% 的项目创建于 2025 年或之后，Model Infra 的这一比例只有 17%。Agent 产品和 Runtime 很年轻，下面承担模型服务、训练、调度、数据处理的系统则积累了更长时间的工程经验。新的 Agent 工作负载正在进入这些成熟基础设施：任务可能短时爆发，多次调用模型和工具，中途等待、重试，甚至在进程结束以后仍然保留外部影响。

这些趋势解释了全景图为何向 Runtime 延伸，也引出了更难的一段：当 Agent 开始参与真实项目，代码供给增加以后，公共仓库里的协作能力有没有同步增长？

## PR 的增长已经成为最明显的协作压力

2026 年前八个月，Top 100 仓库共开启 34.98 万条 Issue 和 60.67 万条 PR，平均每条 Issue 对应 1.73 条 PR。月度比例从 1 月的 1.35 上升到 8 月的 2.11。到 8 月，一个月的新开 PR 已达到 11.16 万条。

这种增长遍布多类仓库。Agent Application 的 PR 队列差额最大，Framework、Runtime 和 Model Infra 同样出现了普遍增长：21 个 Agent Framework、15 个 Agent Runtime 和 36 个 Model Infra 仓库，在 2026 年全部出现 PR 正增长。代码变更的增加已经贯穿整条技术栈。

各类仓库的处理结果也有差别。Agent Application 的仓库中位 90 天合入率为 56.6%，Agent Framework 为 68.1%，Agent Runtime 为 73.7%，Model Infra 为 67.8%。应用仓库直接承受快速变化的用户需求，合入压力最大；Runtime 的合入率相对更高，但 15 个仓库全部出现 PR 队列增长。基础设施并没有远离这轮代码供给，它只是以另一种节奏处理变化。

为了判断这些 PR 是单纯“来得更多”，还是已经影响处理结果，我们固定了 55 个在 2024、2025、2026 三个窗口中都可比较的仓库。2024 年前八个月，它们新开与关闭 PR 的差额为 1,426 条；2025 年是 4,459 条；2026 年扩大到 42,772 条。与之相对，2026 年的 Issue 流入与关闭基本持平，关闭量还比新开量多 1,250 条。

仓库并没有在所有工作上同时失速。压力主要集中在需要阅读代码、运行验证、提出修改意见并做出合入决定的 PR 上。

> 【配图 3：在线报告「PR 流入增长与队列差额」图。建议截取 2024—2026 PR opened / closed、PR balance 和固定 90 天结果，不要截取重复的大数字卡。】

我们又把观察时间固定为 90 天，以免 7、8 月刚进入的 PR 因为还没来得及处理而夸大积压。结果依然存在：同一批仓库中，90 天后仍保持 open 的 PR 从 2025 年的 5.5% 上升到 2026 年的 11.3%；仓库中位的 90 天合入率从 77.0% 降到 68.4%。Issue 的 90 天未关闭比例则从 31.7% 降到 28.6%。

这组对照很重要。它把“项目太火，所以数字都变大了”拆开了。Issue 的处理没有同步恶化，PR 的完成速度却变慢。进入仓库的代码更多了，而判断哪些代码适合项目、如何修改、何时合入，仍然需要有限的维护者时间。

核心参与者有没有变少？公开 PushEvent 给出了另一条线索。55 个仓库中，发生过 PushEvent 的账号中位数从 2024 年的 13 个增加到 2025 年的 17 个，再增加到 2026 年的 25 个；完成一半 push 所需的账号中位数由 2 个增加到 3 个。前五个账号承担的 push 占比也从 91.4% 降到 74.1%。

集成圈并未收缩，更多账号进入了写入路径。只是 2025 到 2026 年，PushEvent 账号中位数增长 47%，PR 流入增长 105%。维护力量在扩大，速度没有追上代码供给。

发布节奏也能帮助我们理解这种压力。Top 100 中有 98 个仓库在前八个月至少发布过一次 non-draft GitHub Release，中位仓库有 34 个 release day。llama.cpp 在 243 天中的 241 天发布 Release；Vercel AI 的 15,232 条 Release records 分布在 194 天。这里既有高频迭代，也有 multi-package 和 canary pipeline 产生的自动化记录。仓库早已在用自动化提高交付频率，而 Review、验证和合入仍需要在持续流入的代码中逐项完成。

## 仓库已经为 Agent 写规则，但工作仍主要由人发起

在 Top 100 的默认分支上，92 个仓库已经提交 coding-agent 文件或目录。80 个仓库有多种 coding agent 可共用的 instructions，71 个支持 Claude Code 相关格式，Codex、GitHub Copilot、Cursor 和 Gemini 的专用文件也出现在不同仓库中。

这里统计的不只是 `AGENTS.md`、`CLAUDE.md` 等说明文件，也包括 `.claude`、`.cursor`、`.codex`、`.gemini` 等工具目录。它们都表示维护者已经在仓库里留下了面向 coding-agent workflow 的设置。只有 `.gitignore` 中出现一个目录名，不计入结果。

这些设置并不限于 Agent 应用。36 个 Model Infra 仓库中有 32 个已经出现相关文件，PyTorch、Spark、Iceberg、ONNX Runtime、Milvus、Triton 和 OpenVINO 都在其中。在 86 个能够读取明确 instruction 的仓库里，81 个写到测试或验证，72 个写到 code review，63 个涉及 release 或 dependency 工作。维护者正在把原本依靠经验传递的贡献规则，转成 Agent 可以读取的仓库内容。

> 【配图 4：在线报告「不同技术类型的 coding-agent 设置」。建议截取四类仓库覆盖率及简短说明，避免把相同年份重复写进每一行。】

规则准备好了，Agent 会不会直接替人提出问题、发起 PR？5,000 条线程样本给出的答案很明确：只有 87 条由具名 Agent 账号或 App 开启，占 1.7%。绝大多数 Issue 和 PR 仍由 GitHub User 账号带入仓库。

Agent 的公开活动集中在工作进入仓库之后。5,000 条线程中，有 2,158 条出现具名 Agent 的动作，覆盖 95 个仓库；1,914 条在开启后收到 Agent 响应。在 3,567 条 PR 中，1,342 条出现 Agent Review 或行内 Review 评论，占 37.6%。

历史样本显示，这个位置正在快速扩大。我们在同一组 55 个仓库中，为 2025 和 2026 各取 2,750 条同期线程。出现具名 Agent 或 App 的比例从 19.9% 上升到 46.1%，出现公开 Review 的 PR 从 68.8% 上升到 73.9%。与此同时，7 天内收到仓库维护者响应的线程从 37.1% 降到 31.1%，30 天内处理完成的 PR 从 87.8% 降到 80.3%。更多代码进入 Review，并没有自动缩短整个处理过程。

这组变化比单看“Agent 出现了多少次”更接近维护者的日常感受。自动化可以很快给出第一轮检查，一条 PR 仍可能等待项目成员确认需求、判断实现方向、处理兼容问题，或者在多轮修改后决定关闭。Review 覆盖面提高，说明检查能力正在增长；维护者响应和完成率下降，则说明决定与集成仍是链路中更慢的一段。

到了流程末端，角色又发生变化。在 4,089 条能够识别最后 actor 的已解决线程中，3,618 条的最后公开动作来自 GitHub User 账号，占 88.5%；具名 Agent 或 App 只有 79 条。这里的最后动作包括 merge、close 或 reopen，它不等同于一个人完成了所有工作，却能说明谁在公开记录中改变了线程的最终状态。

> 【配图 5：在线报告「一条公开 Issue / PR 的不同阶段出现了谁」。建议截取 1.7%、37.6%、88.5% 三个阶段，并保留分母说明。】

这条链路呈现出一种具体分工：人和外部贡献者发起工作，Agent 大量进入回应与 Review，最后的仓库状态变化仍主要由 User 账号完成。Agent 没有简单地替代某个角色，它先进入了最容易标准化、也最容易公开记录的中间环节。

## Agent Review 确实推动了更多下一轮修改

Review 是这条协作链中最值得细看的位置。

3,567 条抽样 PR 中，2,521 条出现过正式 Review，占 70.7%；1,342 条出现 Agent Review 或行内 Review 评论，占 37.6%。我们把每条已 Review 的 PR 按时间排列，找到第一次正式 Review，再检查后面是否出现新 commit。2,521 条中有 1,385 条继续提交代码，占 54.9%。

第一次 reviewer 的身份带来了明显差异。具名 Agent 或 App 首先 Review 的 1,249 条 PR 中，有 834 条后续又出现 commit，占 66.8%；GitHub User 首先 Review 的 1,111 条中，有 457 条继续提交，占 41.1%。两组相差 25.7 个百分点。

> 【配图 6：在线报告「第一次正式 Review 之后是否继续提交」。重点保留 Agent 66.8% 与 GitHub User 41.1% 两条对比；70.7%、37.6%、54.9% 作为上方背景数据即可。】

这个差异说明，Agent Review 并没有停留在“留下一条评论”。在这批公开记录里，它更常与下一轮代码修改相连。可能的原因有几种：Agent Review 可以快速覆盖更多文件和规则；Agent 参与较多的 PR 本来就更容易发生反复修改；不同项目调用 Agent 的时机也并不相同。仅凭时间顺序无法把这些因素拆开，但可以确认一件事：Agent 已经进入真实的迭代过程，Review 之后确实更常有代码继续变化。

`CHANGES_REQUESTED` 提供了更严格的观察。当 reviewer 明确要求修改时，161 条 PR 中有 123 条继续提交，占 76.4%。其中 Agent 提出修改要求的 17 条里有 13 条继续提交，占 76.5%；GitHub User 提出修改要求的 137 条里有 106 条继续提交，占 77.4%。两组几乎相同。

这让前面的结果更容易理解。Agent-first Review 整体上更常进入下一轮提交；当 Review 已经给出明确、可执行的修改要求，发出意见的是 Agent 还是 User，后续提交比例都很高。决定后续提交比例的更直接信号，是意见是否具体到足以推动下一次修改。

对维护者来说，这里也有一个现实价值。Agent 可以扩大 Review 的覆盖面，把格式、测试、边界条件和重复问题提前指出。它能把更多 PR 推进到“可以继续改”的状态。仓库真正节省多少时间，还取决于这些意见是否准确、是否重复，以及修改后的代码离合入还有多远。现有数据证明了迭代发生，效率需要继续通过处理时长、返工和后续修复来判断。

## 第一个 Agent patch 进入仓库后，代码会经历几种不同命运

Review 之后继续提交，并不自动意味着第一版代码被接受。为了观察变化发生在哪里，我们从 2026 年线程样本中追踪了 10 个已经合并、且能高置信识别 coding Agent 贡献的 PR，其中 9 个可以从第一版有效 Agent patch 一直追到最终 head。

这 9 个 PR 的第一版 Agent commit 共新增 1,225 行文本。最终版本中，765 行保持完全相同，占 62.4%；123 行被后续 human-account commit 修改或删除，193 行被后续 Agent commit 修改，另有 144 行无法可靠解析后续作者。

> 【配图 7：在线报告「第一版可观察 Agent patch 后来发生了什么」。建议截取 62.4% 总览和 9 个 PR 案例列表。】

总比例说明，第一版 Agent patch 并非普遍会被人重写，大部分精确文本留到了合并版本。案例之间的路径却差异很大。ONNX Runtime #28045 的第一版 patch 有 611 行，533 行原样保留，78 行由后续 User 账号修改；Vercel AI #18818 的 172 行则全部被后续 Agent commit 替换。只看最终 merged diff，会把这两种协作过程都压缩成“PR 已合入”。

对开源项目而言，谁敲下第一行代码正在变得不那么容易回答。更有用的问题是：谁发现了需要解决的问题，谁说明修改方向，谁验证结果，谁愿意在合入后继续维护。Agent 可以在这些位置承担越来越多的具体工作，但公开仓库仍然需要把变化连接到项目规则和长期责任。

## 外部贡献扩大了代码来源，也让最后的判断更重要

Top 100 中，48 个仓库明确邀请外部贡献，12 个要求先开 Issue 或满足一定条件，38 个没有检测到限制，只有 2 个明确采用 collaborators-only。开放 PR 仍然是这个生态的主流协作方式。

在 5,000 条线程样本里，外部账号创建了 66.8% 的 PR。到了固定成熟度检查点，已解决 external PR 中 57.2% 显示为 merged；maintainer 或 member 发起的 PR 则是 82.8%。外部贡献者提供了大部分代码候选，仓库团队拥有更多上下文、权限与持续关系，因此更容易让变化通过合入路径。

生成和提交代码的门槛下降后，贡献入口会容纳更多尝试，项目也更需要清楚说明问题边界、测试要求与接受标准。92 个仓库提交 Agent rules，可以看作维护者对此作出的实际回应：规则正在成为协作基础设施的一部分。

规则的价值还体现在减少无效往返。贡献者或 Agent 在开始修改前就能知道项目使用什么命令、哪些测试必须通过、一个 PR 应该解决多大的问题。维护者因此有机会把重复说明写进仓库，把稀缺时间留给具体设计和例外判断。若规则只告诉 Agent 怎样生成代码，却没有说明验证和 Review 要求，代码产量越高，后面的筛选成本也会越高。

也有项目选择另一种开放方式。DeepSeek Harness 公开 MIT 代码并开放 Discussions，却关闭核心仓库的 Issues 和 PR，把社区开发引向插件。这种设计保留了代码可读和扩展空间，同时把核心修改权收得更紧。代码公开、核心仓库接受外部修改、允许通过插件扩展，是三种不同的治理决定。

当代码供给大幅增加，仓库不一定只能继续扩大同一个 PR 队列。维护者可以把适合标准化的 Review 交给 Agent，把实验性需求导向插件或扩展层，也可以要求贡献者先通过 Issue 对齐问题。关键在于让进入仓库的工作量与项目能够承担的验证、决策和维护能力相匹配。

## Agent 增加了产出，合入和维护仍由项目承担

回到开头的问题：Agent 的出现，究竟提高了效率，还是给维护者增加了负担？

公开数据给出的答案并非单向。Agent 的贡献已经很具体：它参与 43.2% 的抽样线程，覆盖 95 个 Top 100 仓库；37.6% 的抽样 PR 出现 Agent Review 或行内评论；Agent 首先 Review 的 PR 中，66.8% 继续提交代码。它增加了代码生产和 Review 能力，也推动了更多修改循环。

另一边，仓库面对的 PR 数量增长得更快。同一组 55 个仓库的 PR 流入同比增长 105%，7 天内收到维护者响应的线程比例从 37.1% 降到 31.1%，30 天内处理完成的 PR 从 87.8% 降到 80.3%。更多 PR 进入公开 Review，及时完成的比例却下降。现阶段的 Agent 更擅长增加候选方案和检查意见，还没有让项目的判断与合入能力按同样速度扩张。

这会改变我们理解开源贡献的方式。过去，一次贡献往往从“有人愿意写代码”开始；在 Agent 时代，写出一个 patch 会越来越容易。开源项目更需要的是有人提出适合项目的问题，给出可以执行的修改意见，验证结果，并在合入后继续处理后果。

这些工作不一定都由人亲自完成。Agent 可以写代码、Review、运行测试，也可以继续修改自己的 patch。人的位置仍然清楚：决定项目愿意承诺什么，处理规则之外的例外，并为进入主分支的变化承担长期维护责任。5,000 条公开线程里，88.5% 的最终可见状态动作来自 GitHub User 账号，正是这种责任在 GitHub 上留下的痕迹。

所以，Agent 时代的开源协作不会因为代码更容易生成而变得次要。代码越多，协作越要回答一个朴素的问题：这个变化是否值得项目长期保留？

一个成熟的开源贡献，最终留下的不只是代码。它还留下被项目理解的问题、经过回应的 Review、可验证的结果，以及后来的人愿意继续维护的决定。

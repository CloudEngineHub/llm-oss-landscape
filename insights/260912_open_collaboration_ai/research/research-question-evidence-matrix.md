# 四个研究问题，现在答到哪一步

版本：2026-08-29。cuDF 改名错误已经修复，主样本为 100 个仓库、2,000 条线程，校验通过。

## RQ1 · Agent 被采纳的比例有多高，主要做什么？

### 已经能回答的部分

- 100 个仓库里，86 个公开了明确的 Agent 指令文件；把活跃配置也算上是 92 个。
- 这叫 `Agent marker` 覆盖，不是 Agent 使用率。它只说明仓库为 Agent 准备了指令或配置。
- 在线程中，可确认 Agent 身份或 App 代理行为出现在加权总体的 **40.35%**；仓库等权是 **42.8%**。100 个仓库里有 89 个至少抽到一条可见 Agent 参与线程。
- 把两个“看起来像 Agent、但功能证据不足”的账号全部算进上界，结果只从 40.353% 变到 40.378%。这部分身份不确定性没有改变结论。
- Agent 最常见的公开任务不是独自发起 PR，而是 code review、讨论回复、triage / routing 和 work linking。Agent 只发起了加权总体的 **0.87%**，但参与了 **36.43%** 的后续回复，并出现在 **32.65%** 的 PR review 中。

### 仍然看不到的部分

开发者本地使用 Cursor、Claude Code 或 Codex，最后仍以普通 `User` 账号提交时，GitHub 公共数据无法识别。因此 40.35% 是公开可见参与的下界，不能写成“40% 的代码由 Agent 完成”。

## RQ2 · Agent 如何与开发者协同，真正进入软件迭代？

### 已经能回答的部分

- 100 个仓库都启用 PR；98 个允许任何人创建，Codex 和 Claude Code 的 GitHub 创建策略为仅 collaborators。这个设置来自仓库 API，不再用“是否观察到外部作者 PR”反推。
- GitHub `User` 账号在 **99.4%** 的加权线程里至少出现一次。
- 发起之后有人类账号回复的比例是 **50.99%**，有维护者关联账号回复的比例是 **28.83%**。
- 在能看到最终 gate 账号的已解决线程中，GitHub `User` 执行 **78.3%** 的 gate；维护者关联账号执行 **35.88%**；可确认 Agent 执行 **3.85%**。App 代理 User 时这些类别可能重叠。
- **59.8%** 的加权 PR 出现可见 review；这些 PR 中 **54.23%** 在第一次 review 后继续提交。收到 `CHANGES_REQUESTED` 的 PR 中，**73.08%** 后来又有 commit。

目前更像一条交接链：人或 Agent 提交入口 → Agent 和自动化参与回复、review、分流 → 有责任主体的账号完成判断。数据不支持“Agent 已经普遍独自跑完整个开源协作流程”。

### 不同项目不是同一条路径

分组比较发现，经过多重比较修正后仍有三项差异成立：

- Model Infra 的人类 review 比例高于 Agent Application；
- traditional 仓库的人类 review 比例高于 LLM-native；
- LLM-native 仓库“回复只有自动化账号”的比例高于 traditional。

这说明基础设施和 Agent 应用的协作机制不能混成一个平均数。详见 [不同类型仓库的比较](collaboration-strata-findings.md)。

## RQ3 · Agent 提高效率，还是增加维护者负担？

### 当前最诚实的回答：两种信号同时存在，因果结论还不成立

横截面上，可见 Agent 参与线程的 GitHub merge flag 比例更高、open 比例更低，但评论、review 和可见响应事件也更多。Agent 可能提高了迭代，也可能只是更常被派到重要、困难或已经卡住的线程。

10 个仓库的阶段研究给出了更具体的证据：

- 2025 年末到 2026 年当前，可见 Agent 参与的仓库等权均值从 **35.7%** 升到 **53.3%**；
- 维护者账号参与从 **50.7%** 降到 **35.0%**；
- 30 天内合入 PR 从 **64.4%** 降到 **54.4%**；
- 但在 10 个仓库的配对检验和多重比较修正后，没有一项达到 q < 0.05。方向值得追踪，不能写成普遍规律。

仓库案例也互相反驳：

- LangChain 的 Agent 可见参与大增，同时维护者参与下降；
- Coder 的 Agent 参与增加，30 天内合入反而上升；
- PyTorch 的 Agent 参与增加，但维护者 gate 基本没有撤掉。

长期对照也显示，PR 流入增加和 backlog 压力并非 Agentic AI 独有：2026 年固定成熟度下，Top 100 的未解决 PR 仓库中位数是 9.1%，十二个长期对照仓库是 8.2%；其中多数传统仓库从 2022 到 2026 也出现压力上升。

所以现在能说的是：Agent 带来了真实的修改循环，也可能把更多判断工作推向维护者；净生产率效果尚未被证明。

## RQ4 · 代码变便宜以后，什么贡献仍然稀缺？

### 新增：公开可归因的 Agent 代码下界

- 在 852 个已合入样本 PR 中，3 个满足高置信 Agent-only；概率加权占比为 **0.37%**。
- 这三个 PR 最终新增 318 行；概率加权后约占全部已合入 PR 最终新增行的 **0.14%**。
- 3,729 个已合入样本 commit 中有 23 个 author 是高置信 Coding Agent；概率加权占比为 **0.67%**。
- 高置信 Agent 发起或提交过代码的已合入 PR 为 10 个，加权占比 **1.01%**。多数 Agent-visible 代码工作仍然伴随人类 commit。
- 详细口径、案例和误判修正见 [Agent 代码归因实验](collaboration-agent-code-findings.md)。

这些数字是公开证据下界。普通账号未披露的本地 AI 使用仍然不可见，不能据此声称实际只有 0.14% 的代码由 AI 生成。

### 当前证据支持的方向

- 外部账号贡献了加权 PR 流入的 **73.35%**；
- 到固定成熟度，已解决外部 PR 中 **41.04%** 带 GitHub merged flag，维护者 / 成员 PR 是 **78.62%**；
- review 后继续提交和修改请求后的 commit 很常见，说明“交一个 patch”和“把变更推进到仓库可接受状态”是两件事。

因此，更稀缺的贡献可能是：选对问题、理解仓库约束、给出测试和复现证据、降低 reviewer 的不确定性、完成修改循环，以及最后愿意承担维护责任的判断。

### 还没有完成的度量

这仍是研究方向，不是已经定稿的贡献指数。下一步还要补：

- 合入后 30 / 90 天的 revert 和 follow-up fix；
- 测试、benchmark、复现材料是否真的减少返工；
- 首次贡献者是否继续参与；
- review、triage 和问题定义是否让其他贡献更快进入明确决定。

## 证据等级

| 等级 | 含义 | 例子 |
| --- | --- | --- |
| A | 直接公开观察 | Issue / PR、timeline、review、commit、带日期 Git 对象 |
| B | 项目公开规则 | CONTRIBUTING、AGENTS.md、workflow、仓库设置 |
| C | 聚合或覆盖不完整的数据 | ClickHouse 仓库—年份计数、搜索总体量 |
| D | 解释或研究假设 | 机制推断、案例编码、候选贡献指标 |

涉及效率和因果的说法，不能只靠 A 级横截面差异。需要时间对照、固定观察期、反例和更可信的识别设计。

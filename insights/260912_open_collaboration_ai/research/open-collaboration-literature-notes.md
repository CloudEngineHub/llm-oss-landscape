# 外部实证文献笔记：开源协作与 Coding Agent

更新日期：2026-08-29

这些研究用于补充背景和核验方法。它们的样本不能替代本项目的 Top 100 仓库研究，也不能把不同论文的估计合并成同一个总体指标。

## 生产率结果高度依赖任务与开发者情境

- [Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) 随机分配了 246 个真实任务，由 16 名熟悉相关仓库的资深开发者完成。在 2025 年初的工具条件下，允许使用 AI 的任务反而多花了 19% 时间，尽管参与者主观上认为自己更快。作者明确警告，不能把结果推广到全部开发者或后续工具。
- [We are Changing our Developer Productivity Experiment Design](https://metr.org/blog/2026-02-24-uplift-update/) 解释了 METR 为什么没有把后续实验当作一次干净的更新：越来越多开发者拒绝参加“不允许使用 AI”的条件，产生选择偏差。这与我们的采纳事件设计直接相关——自愿采纳并不是随机处理。
- [Research Update: Algorithmic vs. Holistic Evaluation](https://metr.org/blog/2025-08-12-research-update-towards-reconciling-slowdown-with-time-horizons/) 指出，即使 Agent 生成的变更通过测试，仍可能需要补测试覆盖率、格式化、lint 和整体代码质量工作。因此，“通过 CI”不足以代表输出已经达到维护者可接受的状态。

## Agent 生成的 PR 已经多到值得研究，但归因结果取决于识别方法

- [AIDev: Studying AI Coding Agents on GitHub](https://arxiv.org/abs/2602.09185) 及其[开放数据集](https://huggingface.co/datasets/hao-li/AIDev)通过具名 Coding Agent 工作流识别 PR。不同数据版本的截止日期和 Agent 覆盖不同；当前主卡片描述的 v4 截止到 2025 年 11 月，并链接了截止到 2026 年 3 月的 v5 tag。使用其中计数时，必须引用确切版本。
- [On the Use of Agentic Coding: An Empirical Study of Pull Requests on GitHub](https://arxiv.org/abs/2509.14745) 研究了 157 个项目中的 567 个 Claude Code PR。论文观察到大量重构、文档和测试任务，报告合入率为 83.8%，且 45.1% 的已合入 PR 还经历了进一步人工修改。这是经过筛选的 Claude Code 语料，不能作为全部仓库工作的采纳率分母。

## Review 与任务选择正在成为主要压力点

- [Where Do AI Coding Agents Fail?](https://arxiv.org/abs/2601.15195) 分析约 33,000 个 Agent 生成的 PR，并人工编码了 600 个失败案例。文档、CI 和构建更新比性能优化、bug 修复更容易合入；变更规模过大、检查失败、重复提交、不需要的功能和 reviewer 参与不足，是反复出现的失败信号。
- [From Industry Claims to Empirical Reality: An Empirical Study of Code Review Agents in Pull Requests](https://arxiv.org/abs/2604.03196) 在 AIDev 衍生样本中比较纯人工 review 与纯 Code Review Agent review。该语料中，只有 CRA 参与的 PR 合入率更低；在被放弃的案例中，低信号自动反馈很常见。这支持我们把“发生过 review”和“发生过有价值的把关决定”分开测量。
- [Security in the Age of AI Teammates](https://arxiv.org/abs/2601.00477) 发现，安全相关 Agent PR 集中在测试、文档、配置、错误处理和加固任务；相较其他 Agent PR，它们合入率更低、review 延迟更长，与高风险变更受到更严格审查的解释相符。
- [Understanding the Rejection of Fixes Generated by Agentic Pull Requests](https://arxiv.org/abs/2606.13468) 对 306 个被拒绝的 Agent 修复进行质性编码。方案错误、验证失败、执行不完整和低优先级工作，都会消耗 review 或计算资源，却不产生被接受的变更。好的任务选择和仓库特定约束，本身就是贡献的一部分，而不是代码之外的附属开销。

## 多 Agent 带来的是协调问题，不只是更高吞吐

- [AI Agent Pull Requests on GitHub: Frequency, Structure, and Merge Conflict Rates](https://arxiv.org/abs/2607.04697) 研究 AIDev 中并发出现的 PR。其语料里的跨 Agent 配对较少，但文本冲突率高于同一 Agent 的配对。这一发现提示我们测量并发工作、所有权和冲突；同时它仍只是下界，因为 Git 的文本合并无法识别语义冲突。

## 对本研究的启示

外部文献得出不同方向的结果，是因为它们研究的分析单元不同：实现时间、Agent 生成的 PR、自动化 review、安全变更或合并冲突。我们的报告不应追求一个通用的“AI 生产率”数字，而要始终保留四条边界：

1. 仓库是否为 Agent 工作做好公开准备；
2. 可观察、可归因于 Agent 的 Issue、PR 或 review 活动；
3. 达成决定所需的 User 与维护者工作；
4. 已接受变更的持续性与下游后果。

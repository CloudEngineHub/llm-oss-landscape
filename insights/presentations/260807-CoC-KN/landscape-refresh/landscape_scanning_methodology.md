# Agentic AI 全景图的项目扫描方法

> CommunityOverCode China 2026 keynote 工作方法。当前数字对应 2026-07-28 快照；扫描框架可以在后续全景图更新中复用。

## 一句话版本

**先用数据把网撒宽，尽量别漏；再回到生态结构，判断谁真的值得留在图上。**

机器适合做候选发现和重复劳动。最后的取舍仍然需要人回答一个问题：这个项目是否帮助我们看清生态正在长出什么。

## 这次扫描的漏斗

| 阶段 | 数量 | 这一层回答什么 |
|---|---:|---|
| 扫描时全景图基线 | 227 | 哪些项目已经在图里 |
| 原始候选池 | 6,118 | 最近可能值得关注的仓库有哪些 |
| 自动相关性过滤 | 878 | 哪些仓库确实与 Agent、Model Infra 或开放模型有关 |
| GitHub 实时复核 | 227 | 项目现在是否仍有效，定位有没有变化 |
| README 二次判断 | 222 | 项目的实际技术定位是否与简短描述一致 |
| 人工编辑 | 24 | 哪些建议补入，哪些需要继续观察 |

最终留下 12 个 A 档项目和 12 个 B 档项目。这里的 6,118 是高召回候选池，不是 6,118 个 Agentic AI 项目。

2026-07-28 刷新完成后，这 24 个项目已经写入 `data/agentic-ai-projects.csv`，当前表共 251 个项目。A/B 档只属于扫描阶段的编辑过程，不再作为长期字段保留；主表改用 `landscape_action` 明确记录 keep、add、remove 和 omit。

## 第一步先保证召回

原始候选来自三个入口，最后按稳定的 GitHub repo ID 去重，并排除当前图中的 227 个仓库。

### 近期关注度

从 OpenDigger `opensource.events` 中查询 2026-05-01 至 2026-07-28 可见的 GitHub WatchEvent，取仓库前 2,500。

这一组容易发现刚刚获得大量关注的新项目。它只承担候选发现，不解释成精确 star 增长。近期 GitHub 事件数据存在覆盖缺口，GitHub 公开 stargazer 明细接口也已经收紧。

### 近期社区活动

从 `opensource.global_openrank` 查询 2026-04、05、06 三个已结束月份的 Repo OpenRank，三个月相加后取前 4,000。

这一组可以找到传播声量一般、开发协作却很活跃的项目。它也能避免扫描结果完全被历史累计 stars 支配。

### GitHub 定向搜索

针对 `agentic`、`coding agent`、`agent framework`、`agent memory`、`computer use`、`MCP`、`LLM inference`、`model serving` 和 `post-training` 等方向做 12 组搜索。

搜索结果要求近期仍有 push，并根据类别设置 100、300 或 500 stars 的最低门槛。每组最多读取前 100 个结果。这一层用来补 OpenDigger 尚未覆盖或回填较慢的新仓库。

三个入口取并集后，得到 6,118 个不在现有全景图中的 repo ID。

## 第二步判断它是不是相关项目

自动过滤会读取四类文本：

- repository name
- description
- topics
- README 前 8,000 个字符

关键词分为 Agent、Model Infra 和 Large Models 三组。Agent 相关词权重最高，模型训练、推理、评测等基础设施词其次。

```text
相关性分数 =
Agent 关键词数量 × 4
+ Model Infra 关键词数量 × 2
+ Model 关键词数量 × 2
- 教程和合集关键词数量 × 3
```

`awesome-*`、课程、prompt/skill 合集和教程仓库会被降权。它们能反映传播热度，却很少代表一个可以长期追踪的技术项目。

这一轮把 6,118 个候选缩小到 878 个。

## 第三步回到 GitHub 看项目现在是什么

从 878 个项目中分别取：

- 可见 WatchEvent 排名前 100
- OpenRank 排名前 100
- GitHub 搜索排名前 80

三组取并集后，通过 GitHub API 更新当前名称、stars、许可证、最近 push、fork 和 archive 状态。失效仓库、fork、归档项目以及已经出现在图中的项目被移除。

接着读取高信号项目的最新 README，再判断一次相关性。很多误判是在这里暴露的：仓库描述可能只写了一句营销文案，README 才能看出它是通用框架、垂直应用，还是教程集合。

这一轮最后保留 222 个机器候选。

## 第四步由人决定全景图要表达什么

机器分数只决定“值得看一眼”。进入主图还要检查下面几件事。

### 它有没有补上结构缺口

OpenViking 的意义在于 context database 开始独立成层。LMCache 让 KV cache 成为可持久化、跨引擎复用的基础设施。这类项目能帮助全景图表达新的技术结构。

### 它是不是通用能力

协议、框架、runtime 和基础设施通常可以支撑多种 agent。单一行业应用只有在开创了新类别时，才适合占据主图空间。

### 它和现有项目是不是在重复表达

同一公司的一组产品仓库、主项目拆出的 SDK、同一类别中高度相似的工具，需要做替换或谱系说明。全景图的空间有限，logo 数量本身没有分析价值。

### 它是否带来了被忽略的开发者生态

Koog 的 stars 不是最高，但它补上了 JVM/Kotlin Agent Framework。vLLM-Ascend 补上了 CUDA 之外的硬件生态。这种代表性对 Apache 开发者受众尤其重要。

### 证据能不能支撑“现在就放进去”

只有短期关注度、缺少持续活动数据的项目先进入 B 档。项目已经形成清晰类别、当前协作活跃，并且和现有图没有明显重复时，才进入 A 档。

## A 档和 B 档分别是什么意思

**A 档建议补入**：项目已经补足结构缺口，当前数据和官方材料能够支撑其代表性，可以进入下一版全景图。

**B 档候补观察**：技术方向值得追踪，但仍有重复度、成熟度、社区独立性或数据完整性问题。下一次更新时继续复核。

分档不是项目质量排名。它表达的是全景图编辑决策。

## 数据口径必须一起讲

- GitHub stars 使用 2026-07-28 当前快照，只描述关注度。
- WatchEvent 存在近期覆盖缺口，只用于发现候选。
- OpenRank 使用 2026-04 至 06 月，但 05、06 月仍可能继续回填。
- OpenRank 的近期下降不能直接解释为项目或生态活跃度下降。
- Large Models 层需要额外查看模型发布、权重、许可证、评测和真实使用，GitHub repo 扫描只能提供部分线索。

这套方法适合回答“哪些项目可能被漏掉”和“全景图正在缺少什么”。它不适合制作精确的 star 增长排行榜，也不用于给开源项目做质量总排名。

## 分享时可以这样讲

下面这段控制在 80–90 秒：

> 每次更新全景图，最麻烦的其实不是画图，而是怎么知道自己漏了谁。
>
> 这次我们先把网撒得很宽。我们从最近的 GitHub WatchEvent 里拿了 2,500 个仓库，从 4 到 6 月的 OpenRank 里拿了 4,000 个，再加上十几组针对 agent、MCP、inference 和 post-training 的 GitHub 搜索。去重并排除旧图以后，一共有 6,118 个候选。
>
> 接下来机器帮我们读仓库名称、description、topics 和 README，把教程、合集和明显无关的项目先拿掉。6,118 变成 878，再通过 GitHub API 更新项目状态，最后留下 222 个值得人工看一眼的仓库。
>
> 最后的判断没有交给一个综合分。我们会看它有没有补上全景图的结构缺口，是不是通用基础设施，和现有项目有没有重复。最后得到 12 个建议补入项目和 12 个候补。
>
> 所以这张图不是按 stars 排出来的。数据帮我们尽量别漏，最后还是要回答：这个项目有没有帮助我们看懂生态。

## 方法论页怎么画

建议只用一页漏斗，不展示复杂公式：

```text
WatchEvent Top 2,500 ─┐

GitHub 定向搜索     ──┘     撒网    相关    复核    编辑
```

> 数据负责尽量别漏，编辑判断负责让全景图仍然有意义。

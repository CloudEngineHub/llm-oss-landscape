# 《Agent 进入开源协作之后》10 分钟演讲稿

对应页面：`/presentations/260910_inclusion/present`

## 01｜开场（00:35）

大家好，我是 Xiaoya。

今天分享的是 Ant Open Source 和 InclusionAI 对 Agentic AI 开源生态的一次联合研究。我们先整理了 143 个基础设施项目，再进入最活跃的 100 个仓库，检查今年以来约 95.7 万条 Issue 和 Pull Request，并从中抽取 5,000 条线程，逐条还原公开协作过程。

我想回答两个具体问题：技术供给正在往哪里移动；当 Agent 开始参与 GitHub 的回应、Review 和代码修改之后，项目的协作效率有没有随之提高。

## 02｜Agent Infra 全景（00:55）

*先停留在完整全景图；讲完第一段后按右箭头，显示图下方的信号。*

这是最新的 Agent Infra Landscape，一共 84 个项目。图中的项目按照一次 Agent 工作需要经过的系统层次来组织：最上面是面向用户的应用，中间是 Framework，下面是 Runtime，包括上下文、协议、工具调用、隔离和可观测性。

应用仍然吸引最多公开活动。32 个应用项目贡献了 7 月 55% 的 OpenRank，OpenClaw、Hermes Agent、Deer Flow、Lark CLI 和 OpenViking 是当月最活跃的一组项目。不过新增供给已经开始向下移动：相较 5 月追踪池，新进入版图的 23 个 Agent Infra 项目中，13 个属于 Runtime。

新增项目所处理的问题已经从应用延伸到长期上下文、系统连接、执行边界和结果证据。做出一个能演示的 Agent 之后，越来越多项目开始补长期运行需要的工程。

## 03｜Model Infra 全景（00:55）

*先展示完整 Model Infra；按右箭头后再讲图下方的信号。*

这是 59 个 Model Infra 项目。它的年龄结构和 Agent Infra 很不一样：2025 年以后创建的项目只占 17%，大量能力来自已有模型系统的持续演进。

不过活跃度同样高度集中。Serving 单独贡献约 44% 的 7 月 OpenRank；加上 Pre-Train，两层合计占到 75%。SGLang、vLLM、Ollama 和 FlashInfer 的竞争，把关注点推向推理吞吐、延迟、硬件效率和稳定调用。

所以 Agent 热潮并没有让 Model Infra 退到背景里。每一次长上下文、工具调用和多轮执行，最后都会落到模型怎样被稳定、快速地服务出来。Serving 是 Agent 扩张最直接拉动的模型基础设施层。

## 04｜版图里的增长与缺口（01:05）

把项目分类与 4 月到 7 月的 OpenRank 变化放在一起，会看到三个方向同时升温。Lark CLI 增长 83.9，对应靠近开发者的终端入口；OpenViking 增长 42.6，对应长期上下文和记忆；FlashInfer 增长 20.7，对应推理内核。DeepSeek Reasonix、Orca 和 Deer Flow 则分别落在编码、多 Agent 编排等位置。

右边把 31 个 Runtime 项目沿一次执行过程排开：9 个做 Context，8 个做接口和协议，6 个负责工具、浏览器或计算机操作，Sandbox 和可观测评估各有 4 个。越靠近信息获取，项目越多；越靠近隔离、审计和结果验证，供给越少。

增长横跨入口、上下文、推理内核和多 Agent 编排，一条完整工作链正在被同时拉动。入口、上下文和推理效率已经形成竞争，生产环境需要的隔离与结果证据仍然相对薄。

## 05｜研究设计（00:55）

进入协作研究之前，我先说明每个数字来自哪一组证据。

Top 100 是从 277 个追踪项目中按 2026 年 7 月 OpenRank 选出的活跃仓库。它用于检查仓库类型、协作规则、Agent 文件、Release，以及今年以来的全部 Issue 和 PR。

年度比较使用固定的 53 个仓库：它们今天仍在 Top 100，并且在 2024 年 1 月之前已经公开。每年都取相同的 1 月到 8 月窗口，避免新项目加入改变样本成员。

协作链路使用 5,000 条均衡样本，每个仓库固定 50 条，一共包含 1,433 条 Issue、3,567 条 PR 和 13.8 万个公开事件。固定配额可以保留每个仓库的可比切片，但它不是按真实流量加权的全网比例。

最后还有 10 个仓库的同期面板、10 条 Agent 修改过代码的已合并 PR 和 7 个可阅读案例。它们分别用来比较效率、还原代码沿革和解释协作机制。

## 06｜协作规模：PR 的增长远快于 Issue（01:05）

先看今年以来的全量活动。Top 100 在 1 月到 8 月打开约 60.7 万条 PR 和 34.9 万条 Issue。每月的 PR-to-Issue ratio 从 1 月的 1.35 上升到 8 月的 2.11，进入仓库的改动提案越来越多。

这个趋势在固定 53 个仓库里仍然成立。2025 到 2026，Issue 从 72,300 条降到 68,500 条，下降约 5%；PR 从 124,700 条增至 246,000 条，增加 97%。因为仓库成员和观察月份没有变化，这个差距不是由一批新项目突然加入造成的。

这些 PR 包含人类、传统自动化和可能由 Agent 辅助的提交，我们不能把 97% 全部归因给 Agent。但维护工作的入口已经发生变化：项目收到的问题略有下降，却要判断接近翻倍的代码改动。Review、验证和取舍会因此成为更大的日常工作。

## 07｜Agent 在公开链路中的位置（01:10）

这张表按同一条公开协作链分成四个阶段：发起工作、参与回应、参与 PR Review，以及执行最后一次公开的合并或关闭动作。

5,000 条样本中，由可识别 Agent 或 App 直接打开的只有 87 条，也就是 1.7%。到了回应阶段，Agent 出现在 38.3% 的线程；在 3,567 条抽样 PR 中，37.6% 出现过 Agent Review。最后执行状态变更时，Agent 比例又降到 1.9%。

GitHub User 账号几乎贯穿整个链路：94.6% 的工作由 User 发起，60.1% 的线程出现 User 回应；在能识别最后执行者的已解决线程里，88.5% 的最后公开动作来自 User。仓库团队账号在 Review 中占 35.2%，在最后状态动作中占 52.4%。这些列会重叠，因为“仓库团队”描述的是账号与仓库的关系，而 Agent 也可能通过 App 代替一个 User 执行动作。

这里的 Agent 是保守口径。CodeRabbit、Gemini Code Assist、OpenHands 等公开身份可以被识别；开发者在本地使用 Cursor、Claude Code 或 Codex 后以普通账号提交，公开元数据无法区分。表里的比例描述可验证的公开协作，不等于全部 AI 辅助开发。

## 08｜Review 与代码沿革（01:00）

只统计“Agent 提交过代码”看不到代码怎样进入项目。3,567 条抽样 PR 中，70.7% 出现过 Review；完成第一次 Review 后，55% 继续产生新的 commit；收到 Changes requested 的 PR，76.4% 继续提交。Review 经常开启下一轮修改，一次审查很少概括完整的协作过程。

我们又追踪 10 条已合并、并且有 Coding Agent 改动代码的 PR。其中 9 条可以还原行级历史。第一笔 Agent patch 一共包含 1,225 行，合并时有 765 行原样保留，占 62.4%；123 行后来由人类账号修改，193 行由后续 Agent 修改，144 行无法确定作者。

具体看，ONNX Runtime #28045 的第一笔 611 行里保留了 533 行，后续人类账号修改 78 行。OpenHands SDK #2614 最初的 11 行没有原样留下，后来由人修改 4 行、Agent 修改 7 行。Vercel AI SDK #18818 的 172 行则全部被后续 Agent 提交替换。

同样是“Agent 参与并最终合并”，背后可能是直接保留、人类接手或 Agent 继续重写。代码沿革比一个 merged 标签更能说明协作到底怎样发生。

## 09｜效率实验：吞吐增加，及时响应下降（01:15）

最后回到最核心的问题。我们固定观察 Codex、Claude Code、LangChain、Dify、n8n、Langfuse、Coder、Milvus、vLLM 和 PyTorch，比较 2025 与 2026 年相同的 5 月到 8 月窗口。

进入这些仓库的 Issue 和 PR 从 38,400 增至 101,900，是原来的 2.65 倍；公开可见的 Agent 参与从 33.5% 升到 54.4%。但 7 天内出现维护者回应的比例从 42.9% 降到 20.0%；Issue 30 天内关闭从 48.7% 降到 38.4%；PR 30 天内合入从 70.8% 降到 54.6%。每条线程的可见维护者动作几乎没有变化，仍在 1.4 左右，于是相同的注意力被摊到大得多的任务队列中。

再只看 2026 年，前 24 小时出现 Coding 或 Review Agent 的 PR，30 天合入率是 48.7%；未见这类 Agent 的 PR 是 47.2%，结果接近。差异主要发生在过程：前者平均有 4.67 轮公开对话，后者是 3.00；第一次 Review 后的 commit 分别为 3.94 和 0.76。

这组比较不能证明响应下降由 Agent 单独造成。项目热度、任务难度和仓库阶段都可能影响结果。它能支持的结论是：Agent 让代码供给和公开迭代增长得更快，但在这批仓库里，还没有把更多迭代稳定地转化成更快的响应和合入。

## 10｜DeepSeek Harness 的治理选择（00:50）

DeepSeek Harness 提供了另一种协作设计。它在 2026 年 8 月 13 日开源，17 天获得超过 20.4 万 Stars 和 2.36 万 Forks，传播速度非常快。

仓库采用 MIT 许可证，代码可以自由使用；核心仓库关闭 Issues 和 Pull Requests，只开放 Discussions，并把外部扩展导向 dsh-plugin。贡献指南把官方代码定位为参考实现和灵感来源，社区开发主要在核心仓库之外继续。

代码许可、核心仓库的贡献入口和插件生态是三项独立的治理选择。一个项目可以非常开放地发布代码，同时把核心开发保持在较小团队内，并把社区创新安排到核心仓库之外。

## 11｜结论（00:35）

把版图和协作记录合并来看，几组数据落在同一条变化链上。

开源技术供给正在从应用扩展到 Runtime、Serving、隔离与结果证据。Agent 已经进入 GitHub 的回应、Review 和代码修订，但很少发起工作，也很少执行最后的状态变更。同期面板里，任务吞吐和迭代明显增加，及时响应和 30 天结果却没有同步改善。

代码生成正在变得更便宜。协作能力仍取决于谁来筛选改动、验证结果、完成责任交接，并最终代表项目作出承诺。
